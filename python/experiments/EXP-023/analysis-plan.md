# Analysis Plan: Experiment EXP-023

## Objective

Determine whether the registered CF-AVWAP-001 baseline signal qualifies under
the frozen Phase 004 suite when generated by the cTrader strategy-host branch
and evaluated on emitted real OHLC prices. Also report the original AVWAP
strategy metric book: prevalence, successful-bounce behavior, expectancy,
risk-adjusted model-vs-raw comparison, and diagnostics by instrument, domain,
direction, and `is_pyramid_bounce`.

## Methodology

### Step 1: Dependency, Registry, and Suite Manifest Check

- **Method**: Deterministic artifact and registry validation.
- **Why this method**: EXP-023 is authorized only after EXP-020/021/022 support
  the component gates and after the frozen suite is available. A manifest check
  prevents silent changes to candidate definition, suite thresholds, or the
  D-dogfood-book reference.
- **Simpler alternative considered**: Hardcoding the known statuses and MDEs.
  Rejected because the pipeline should fail loudly if an upstream artifact is
  missing, revised, or inconsistent.
- **Assumptions**: The authoritative candidate definition is
  `CF-AVWAP-001/HYP-004`; the frozen suite is `{strict gate stack, EXP-012
  ratified-loose/fallback, EXP-018 revised portfolio-fitness unit}`; the
  reference book is EXP-019 D-dogfood-book Donchian(20).
- **Expected output**: `dependency_manifest.csv`, `suite_manifest.csv`, and
  blocker rows if any dependency is absent or inconsistent.

### Step 2: cTrader Run Admission and Holdout Fence

- **Method**: Load cTrader strategy-host outputs lazily, validate schema and
  parameters, assert every `SourceCloseTime < AnalysisEndUtc`, and check that the
  AVWAP C# fixed-Parquet smoke reproduces the approved Python reference behavior
  before cTrader-feed runs are admitted.
- **Why this method**: Strategy generation must happen in cTrader, but the Python
  pipeline must still verify that emitted rows obey the holdout fence, parameter
  freeze, and schema contract before any suite result is trusted.
- **Simpler alternative considered**: Route every run directly into the suite.
  Rejected because a malformed or unfenced cTrader run could create a false
  market result.
- **Assumptions**: `SourceCloseTime` is the temporal authority for cTrader
  strategy runs; emitted `RealOpen/RealHigh/RealLow/RealClose` are the only
  valid return basis; cTrader run metadata records domain settings and AVWAP
  parameters.
- **Expected output**: `run_manifest.csv`, `holdout_fence_checks.csv`, optional
  `csharp_avwap_smoke_checks.csv`, and admitted run paths for the 12
  instrument/domain cells.

### Step 3: Standalone Frozen-Suite Screen

- **Method**: For each admitted AVWAP run, use the existing ingestion pattern:
  `load_emitted_run(...)`, derive next-step real-close returns from emitted
  `RealClose`, align `Position[t]` to `t -> t+1`, compute the within-analysis
  train/test boundary chronologically, and evaluate the strict and
  ratified-loose/fallback standalone referees at `alpha0 = 0.05` with the frozen
  bootstrap settings.
- **Why this method**: This is the validated VAL-002 screening path applied to a
  real Phase 004 candidate instead of the MA dogfood vehicle.
- **Simpler alternative considered**: Rebuild domain bars from local Parquet and
  evaluate Python-generated AVWAP positions. Rejected because EXP-023 requires
  cTrader strategy-host generation and emitted real-price consistency.
- **Assumptions**: Position at `SourceCloseTime[t]` is known after bar `t` and is
  evaluated on the next completed real-close return. The frozen bootstrap handles
  residual dependence; `effective_n` and `block_length` are reported.
- **Expected output**: `standalone_suite_verdicts.csv` with strict and
  ratified-loose/fallback verdict rows, effects, CIs, gate legs, effective N, and
  block length.

### Step 4: Revised Portfolio-Fitness Screen

- **Method**: Align the AVWAP candidate position series `C` and the frozen
  Donchian(20) reference book `R` on the same `SourceCloseTime` and emitted
  real-close return rows. Apply the revised incremental unit unchanged:
  `combined = clip(R + C, -1, +1)`, marginal position
  `m = combined - R`, denominator rows where `m != 0`, real-price marginal
  returns, incremental cost, and the EXP-018 revised gate.
- **Why this method**: HYP-004 explicitly allows qualification through
  portfolio fitness, but only against the frozen reference book. The marginal
  estimator answers whether AVWAP adds edge beyond the existing Donchian book.
- **Simpler alternative considered**: Compare AVWAP standalone returns to
  Donchian returns with a difference of means. Rejected because the validated
  portfolio-fitness unit is already defined and handles overlap, clipping,
  denominator, and incremental-cost semantics.
- **Assumptions**: The reference and candidate are aligned on identical emitted
  return rows; zero incremental denominator is non-reportable; Python does not
  generate a new candidate signal.
- **Expected output**: `portfolio_fitness_verdicts.csv` with marginal gross/net
  effects, denominator counts, revised-gate leg states, and
  `POSITIVE_INCREMENTAL` / non-pass classifications.

### Step 5: Original AVWAP Strategy Metric Book

- **Method**: Build descriptive and robust risk-adjusted summaries from cTrader
  events, diagnostic trades, emitted positions, and emitted real-close returns.
  Report:
  - valid bounce prevalence and executed-entry prevalence;
  - completed favorable/adverse target rates, trend-change counts, and
    unfinished counts;
  - strategy return expectancy on real domain prices;
  - raw/traditional close-to-close log-return expectancy on the same rows;
  - robust risk-adjusted level for model and raw returns:
    mean bps divided by median absolute deviation bps, with a classic mean/std
    ratio as a clearly labeled diagnostic only;
  - splits by instrument, domain, direction, and `is_pyramid_bounce`.
- **Why this method**: The metric book preserves the original AVWAP concept
  without letting the descriptive metrics override the frozen suite verdicts.
  A robust mean/MAD ratio avoids relying on normality while still answering the
  original risk-adjusted-return request.
- **Simpler alternative considered**: Report Sharpe ratio alone. Rejected
  because standard Sharpe assumptions are weak for time-ordered financial
  returns; it remains a secondary diagnostic, not the primary risk-adjusted
  interpretation.
- **Assumptions**: Descriptive metrics do not tune thresholds. Raw-return
  comparison uses the same emitted rows as the model; no percentage improvement
  is computed from zero or near-zero baselines.
- **Expected output**: `strategy_metric_book.csv` and
  `event_trade_diagnostics.csv`.

### Step 6: Qualification Summary

- **Method**: Rule-based summary against the predeclared Evidence FOR / AGAINST /
  inconclusive criteria in `scope.md`.
- **Why this method**: The frozen suite emits component-level verdicts; EXP-023
  needs a transparent screen-level conclusion without changing component logic.
- **Simpler alternative considered**: Rank domains by metric-book performance.
  Rejected because ranking would be an unregistered selection step.
- **Assumptions**: A suite pass can come from standalone strict,
  ratified-loose/fallback, or revised portfolio-fitness. Metric-book diagnostics
  explain the result but do not retune the candidate.
- **Expected output**: `qualification_summary.csv` and `run_metadata.json` with
  `SUPPORTED_STANDALONE`, `SUPPORTED_INCREMENTAL`, `SUPPORTED_MIXED`,
  `REFUTED`, `INCONCLUSIVE`, or `BLOCKED`.

## Visualisations

1. Suite verdict matrix by instrument, domain, and component - shows exactly
   where strict, loose/fallback, or incremental qualification occurred.
2. Standalone and incremental effect forest plot with frozen domain detection
   floors - shows effect magnitude relative to strict, loose, and incremental
   MDEs.
3. Model-vs-raw cumulative real-return plot by domain, using bounded
   instrument panels - shows sequence context without changing verdict logic.
4. Event/trade outcome composition by domain and direction - shows favorable,
   adverse, trend-change, unfinished, and non-executed pyramid counts.
5. Risk-adjusted metric heatmap by instrument/domain - compares model robust
   mean/MAD level with raw/traditional return level.

## Interpretation Guide

- If at least one reportable instrument/domain cell passes strict or
  ratified-loose/fallback standalone screening and all run-admission checks pass,
  interpret EXP-023 as `SUPPORTED_STANDALONE` unless an incremental pass also
  occurs.
- If no standalone cell passes but at least one reportable cell is
  `POSITIVE_INCREMENTAL` against Donchian(20), interpret EXP-023 as
  `SUPPORTED_INCREMENTAL`.
- If both standalone and incremental passes occur, interpret EXP-023 as
  `SUPPORTED_MIXED`.
- If all cells are reportable and no suite component passes, interpret EXP-023
  as `REFUTED`: the baseline AVWAP signal did not qualify despite positive
  component evidence.
- If cTrader AVWAP runs, aligned Donchian reference rows, or smoke-validation
  checks are unavailable, interpret as `BLOCKED` or `INCONCLUSIVE` per
  `scope.md`; do not infer a market verdict.
- If metric-book risk-adjusted model returns are worse than raw returns while a
  suite component passes, report the contradiction explicitly. The suite verdict
  remains the qualification result; the metric book becomes the economic caveat.

## Data-View Comparison Considerations

EXP-023 uses cTrader-emitted strategy-host domain bars and positions. There is
no chart-type comparison. Cross-run and reference/candidate alignment must use
`SourceCloseTime`, never row index alone. Event counts can differ from position
rows and trade rows; each denominator is reported separately.

## Implementation Safety and Performance

- Admit cTrader outputs only after holdout-fence checks pass.
- Use `pl.scan_parquet` and column projection for run manifests; collect only
  admitted first-70% outputs needed for suite evaluation.
- Use `tqdm` over instrument/domain/run/component loops.
- Do not create output directories at import time.
- Keep AVWAP signal generation in cTrader. Python may validate, ingest, align,
  and summarize emitted outputs, but must not regenerate candidate positions.
- Reuse loaded emitted positions and events for plots and metric-book summaries;
  do not re-run cTrader output generation for plotting.
- Keep suite settings, MDE maps, reference-book identity, costs, thresholds,
  denominators, and split semantics frozen.
- Treat zero active, trade, completed-move, or incremental denominators as
  non-reportable/null.
- Keep genuinely sequential cTrader AVWAP logic explicit; do not vectorize in a
  way that changes streaming semantics.
