1. The structure and organisation of the `signal-registry` directory and the individaul signal/strategy theory documents need to be standardised, for proper management and reference. This readme document can store that standardised structure.
2. Within the core theory for some strategy, there are components: hypotheses and assumptions upon which the strategy is built/based; these need to independently evaluated/validated for correctness, reliability and statistical significance, before the signal-generating system itself is validated using our testing framework. This applies to all signals/strategies, and these independent hypotheses should be clearly stated in the registry documents, so experiments can be designed for them specifically, to build up to the full system validation. For exmaple:
    - a strategy like "MA Crossover" is very straight-forward. It can be proceed strategy to validation with our testing framework. 
    - however, a strategy that attempts mean-reversion on a novel calculated/derived series might need to characterise the series for MR first, before designing and testing the strategy as a whole
3. Some strategies would not come complete; it may only have a single signal idea, and we would need to develop it's components (entry, exit, risk/position management) emperically. This could seem like data mining, but as long as its developed with constructive scepticism and strict noise robustness guardrails, that is acceptable.
4. The project would have to employ cTrader's backtester to run strategies, and generate data for some experiments. We'll there include c# cAlgo writing to the research process. The alternative is using a python-based backtesting engine, but the data available is native to cTrader, so should be more practical. 
   1. Testing signals, and generating data and returns to be evaluated need to be done in parity with how the model would be used in realtime (online/stream/event-based), therefore vectorising the backtest would not make any sense for some strategies of considerable complexity. This is why the backtester has to be incorporated into the research pipeline. 
   2. This would require building infrastructure on cTrader to take strategies as a "adapter/interface model" for strategies, and would generate datasets we need for analyses, validation and characterisation (signals, trades, e.t.c). This would also warrant replicating some of our existing python code to c# (not all, only those relevant for signal generation, like the custom chart types, and indicators). All strategy validation tests remain in python.
